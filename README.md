# Faserlauf – Carpentry Website with a 3D Furniture Configurator

> **Demo project.** “Faserlauf Möbelwerkstatt” is a fictional carpentry workshop in Berlin-Neukölln. Prices, lead
> times, address, phone number and history are invented. Before choosing the name, a web search confirmed that no
> carpentry or furniture business uses it (see [`docs/RESEARCH.md`](docs/RESEARCH.md) §1).

## Live demo (GitHub Pages)

**<https://derhoodaus-commits.github.io/faserlauf-furniture-configurator-demo/>**

The live demo is a fully static build of the same site. GitHub Pages has no server, so in this version:

- **Forms send nothing.** The contact form and the quote request keep their validation and then show the usual
  confirmation page, which says clearly that this is a demo and nothing was sent or stored. No request leaves the
  browser (the contact form even uses `method="dialog"`, so it cannot submit without JavaScript either).
- **Everything else runs in the browser, as before:** the 3D configurator (lazy-loaded only on its page), wood
  textures from the Web Worker, price and structural checks, share links, snapshot PNG, **PDF quote** (jsPDF) and GLB
  export.
- No API endpoints, no `/render/` utility page, no server headers: the Content Security Policy comes from the
  `<meta>` tag Astro writes into each page (script/style hashes, `blob:` workers).

Build and check it locally:

```bash
BASE_PATH=/faserlauf-furniture-configurator-demo/ SITE_URL=https://derhoodaus-commits.github.io npm run build:pages
npm run preview:pages   # serves dist-pages/ like GitHub Pages: http://localhost:4322/faserlauf-furniture-configurator-demo/
npm run test:pages      # builds under the sub-path and checks that every internal href/src resolves to a file
```

Output folder: `dist-pages/` (the server build stays in `dist/`). Without `BASE_PATH` the static site is built for
the domain root. In PowerShell set the variables with `$env:BASE_PATH='/faserlauf-furniture-configurator-demo/'`; in
Git Bash prefix the command with `MSYS_NO_PATHCONV=1` so the path isn't rewritten to a Windows path.
`.github/workflows/pages.yml` builds and deploys it on every push to `main`.

## What is it?

A complete website for a furniture workshop with a **3D configurator as its centerpiece**: visitors pick a dining
table, coffee table, bookcase, bench or desk, set the size to the centimeter, choose wood, finish, base and edge
profile, and see the result in 3D in their browser, standing in a simple room if they like, next to a 175 cm person
for scale. The price updates with every change; the design can be shared as a link, downloaded as a PDF quote, a
snapshot or a 3D file, compared with a second variant, and sent to the workshop as a quote request including an
image of the configuration.

## What problem does it solve?

Made-to-measure furniture is hard to buy online: customers can't picture the size, don't know what it costs until
they ask, and workshops spend hours answering “what would it cost in walnut, and 20 cm longer?”. The configurator
answers that in a second, with the workshop's own rules: it **calculates how far a top or shelf sags** under load
for the chosen wood and thickness, warns about borderline designs and blocks combinations a carpenter wouldn't build,
always with a concrete fix. Requests that reach the workshop are complete and buildable.

## The configurator

| Feature | How |
|---|---|
| 5 pieces, all parametric | Every part is generated in code from the configuration (`src/lib/model.ts`): tops with edge profiles, tapered or square legs with apron rails, trestle bases with stretcher, side panels, recessed plinth or feet, housed shelves, back boards, dovetailed drawers with flush fronts. No external 3D models. |
| Real-time adjustment | Length, width/depth, height (1 cm steps), board thickness (standard planed thicknesses), base, edge profile (eased, rounded, chamfered, undercut bevel), shelves, drawers. Number inputs with − / + buttons and sliders; out-of-range input is corrected with an explanation. |
| Checks and impossible combinations | Beam deflection per species (stiffness, density) and load case: warning above L/600, block above L/300, with the minimum thickness that would work. Plus shelf spacing, wall anchoring for tall bookcases, trestle needs ≥ 160 cm, undercut edge needs ≥ 26 mm, lower shelf needs clearance, two drawers need width, ergonomic heights, raw finish on tables. |
| 5 woods, 3 finishes | Oak, beech, walnut, pine, ash. Textures (color, normal and roughness maps, plus end grain) are generated procedurally in a Web Worker: growth rings, latewood, cathedral arches, pores, rays, knots, sapwood, glued boards. Finishes: hardwax oil, matte lacquer, raw. |
| 3D view | Rotate, zoom, pan with mouse and touch (OrbitControls); buttons for rotate, zoom, front/side/top views and reset for keyboard users. Environment lighting from three's procedural `RoomEnvironment`, a shadow-casting key light and contact shadows, studio floor. Grain always runs along the length of each part, end faces show end grain, textures are mapped in real-world units. |
| Dimension lines | Toggleable, outside the piece like on a workshop drawing, labels in cm. |
| Room mode | Floor (oak planks, polished concrete, terracotta tiles) and wall color (5 colors) selectable; optional 175 cm person for scale. |
| Live price | Material (volume × yield × price per m³), workshop time (€78/h, quarter hours), finish (per m²), delivery flat rate (+ two-person surcharge), 19 % VAT, in whole cents. Every wood/base/edge/thickness option shows its price difference. All prices marked as demo. |
| Save and share | The whole state (both variants, compare mode, room, person, dimensions) lives in the URL, updated as you go; “Copy link”. Old or tampered links are repaired, not rejected. |
| Request a quote | Dialog with validation; sends the configuration, an image of the current view and the contact details. The server re-validates the configuration and **recalculates the price** (the browser's price is never trusted), stores the request with the image and returns a reference (`FL-XXXXXX`). |
| PDF quote | jsPDF in the browser (loaded on click): image, specification, price breakdown, notes from the structural check, cut list, demo terms, link back to the configuration. |
| Compare | “Compare with a variant” creates variant B. Both stand **side by side in the same scene at the same scale**, a table highlights every difference and the price gap; on phones you can switch between A and B. |
| Snapshot | PNG of the current view, with the dimension labels drawn into the image. |
| GLB export | `GLTFExporter` (binary glTF 2.0): only the furniture, in meters, with its wood color textures as JPEG (~400 KB). Tested by reading the file's glTF structure. |
| AR | **Left out on purpose**: iOS needs USDZ, Android Scene Viewer needs a public HTTPS URL, WebXR is patchy; none of it can be verified here. The GLB export is the basis to add it later. |
| No WebGL | Feature check before loading; without WebGL the configurator still works (options, price, checks, link, quote request) and shows a clear message with a static picture. |

## Tech and decisions

| Area | Decision | Why |
|---|---|---|
| Framework | **Astro 7** with a **React 19 island** for the configurator | Content pages are static HTML with almost no JavaScript (home page: ~2 KB of JS); the configurator is one island, and its WebGL part is a separate chunk that only loads there. Next.js would ship the React runtime on every page for no benefit; a pure SPA would hurt SEO and first paint. |
| 3D | **three.js r187 + React Three Fiber 9 + drei** | The scene is derived from React state anyway; R3F maps it declaratively and disposes resources on unmount. drei provides OrbitControls, contact shadows, HTML labels, lines and the PerformanceMonitor. |
| Performance | `frameloop="demand"` (no rendering when nothing moves), DPR capped at 1.5 (phones 1.25) and adapted by `PerformanceMonitor`, textures generated once per wood in a Web Worker and shared by all parts, materials cached per wood × finish, geometry rebuilt only when a part's shape changes, smaller textures and shadow maps on phones, everything disposed on unmount | See [`docs/RESEARCH.md`](docs/RESEARCH.md) §4. |
| Lazy loading | Configurator island hydrates `client:only` with a server-rendered placeholder; the viewer is a dynamic import; PDF, GLB exporter and jsPDF load on click | Pages without 3D stay light. |
| Logic separated from rendering | `src/lib/` (pure TypeScript, no three.js): data model, validation, pricing, URL state, form validation, wood generator. `src/configurator/viewer/` turns the parts into meshes. | The same code runs in the browser, on the server (quote check), in the build scripts and in the unit tests. |
| Wood textures | One generator (`src/lib/wood/generator.ts`), used at runtime (Web Worker → `DataTexture`) **and** at build time (`scripts/generate-textures.ts` writes the swatches). Preview images of the furniture are screenshots of the real configurator (`scripts/render_previews.py`). | No copyrighted texture files; every image on the site is output of the project's own code. |
| Forms / server | Astro server endpoints (`/api/inquiry`, `/api/contact`) via `@astrojs/node` in middleware mode, behind a small production server (`server.mjs`): gzip + brotli, cache headers, security headers, clean URLs with trailing-slash redirects, custom 404, path traversal protection | Runs as-is on a small VPS; static pages stay static. |
| Security | Astro's CSP with per-page script/style hashes, `frame-ancestors 'none'`, nosniff, body size limit, honeypot, rate limit (10 requests / 10 min per IP), image magic-byte check, server-side re-validation | No keys or credentials anywhere; `.env.example` only lists port, host and data folder. |
| Fonts | Fraunces (variable, with the SOFT axis) for headings, Hanken Grotesk for text, **self-hosted** from `@fontsource-variable` (OFL) | No Google Fonts request (GDPR). |
| Design | Warm paper, dark-brown ink, one rust accent; the configurator's dimension lines reappear as the site's typographic motif (eyebrows with tick marks, the measured hero image, a ruler-style timeline) | A recognizable, crafted look instead of a template. |
| Language and locale | US English, prices like “€2,329”; the business stays German (Berlin address, 19 % VAT, German postcodes, delivery within Germany) | Written for international clients, true to a Berlin workshop. |
| Phone number | `030 23125 682`, from the number range the German Federal Network Agency reserves for film and TV | Looks real, rings nowhere. |
| TypeScript | `astro/tsconfigs/strictest`, `astro check` runs in every build (0 errors, 0 warnings) | |

## Getting started

Requirements: Node.js 22.23 or newer (Astro 7). Tested with Node 26 on Windows 11.

```bash
npm install
npm start          # type-checks, builds and serves the production site
```

Then open <http://localhost:3002>. `npm run dev` starts the development server on the same port (no CSP in dev
mode). Port, host and data folder can be changed via environment variables or a `.env` file (see `.env.example`).
Quote requests and messages end up in `data/inquiries/` and `data/messages/` (JSON, plus the image as JPEG).

Regenerating the images (only needed after changing the generator, products or gallery):

```bash
npm run generate:textures    # wood swatches → public/generated/wood/ (Node, uses sharp)
npm run generate:renders     # product, gallery, hero and Open Graph images → public/generated/ (Python + Playwright)
```

## Tests

```bash
npm test             # unit tests (Vitest)
npm run build && npm run test:e2e   # browser tests (Playwright for Python, Chromium with WebGL) + screenshots
npm run test:pages   # static GitHub Pages build under its sub-path: every internal URL resolves, no API, no three.js outside the configurator
```

`test:e2e` needs Python with `playwright` (Chromium installed) and, for the PDF content check, `pdfplumber`.
Headless Chromium renders WebGL with SwiftShader (`--use-gl=angle --use-angle=swiftshader`).

**What was tested (all passing):**

- **85 unit tests** (Vitest):
  - *Pricing* (`pricing.test.ts`): reference price of the standard table, VAT and whole cents, quarter-hour
    billing, price goes up with size/wood/edge, finishes, delivery flat rates and two-person surcharge, and
    **1,000 random configurations** that are never cheaper than the advertised “from” price.
  - *Structural checks* (`validation.test.ts`): beam formula against a hand calculation, scaling laws, every default
    and gallery configuration is buildable, blocked/warned spans with the suggested thickness, apron stiffening,
    species stiffness ordering, shelf spacing, wall anchoring, all impossible combinations, normalization of
    out-of-range input.
  - *URL state* (`url-state.test.ts`): round trip of the default state and of **1,000 random states** (both variants,
    compare mode, room settings), readable short URLs, partial links from product pages, tampered and broken links.
  - *Model and 3D geometry* (`model.test.ts`): parts fill the configured size and stand on the floor (also for 500
    random configurations), shelf spacing, drawers, grain direction, cut list; every edge profile produces
    outward-facing triangles of the exact size, textures are mapped in real-world units, tapered legs keep the outer
    corner flush.
  - *Wood generator* (`wood.test.ts`): deterministic, species differ in brightness, rings contrast across the grain
    but not along it, valid normal/roughness maps, seamless noise.
  - *Server endpoints* (`api.test.ts`): valid request stored with image and **server-recalculated price**, unbuildable
    configuration rejected, tampered values normalized, field errors, invalid image ignored, honeypot, broken JSON
    (400), wrong content type (415), oversized body (413); contact form as JSON and as a classic form post (303).
- **376 browser checks** (`tests/e2e.py`, Playwright + Chromium with WebGL):
  - All 17 pages (incl. all 5 product pages) at **390, 768 and 1440 px**: HTTP status, exactly one h1, no horizontal
    scrolling, no console errors, WCAG AA contrast of every visible text (desktop), tap targets ≥ 44 px (phone); plus
    overflow at **320 px**.
  - **The main journey on desktop and on a phone**: home → furniture → product page (breadcrumbs, “from” price) →
    configurator opens with the right piece → change size and wood (price updates, URL follows) → review → quote
    dialog with image → empty submit shows errors → valid submit → confirmation page with reference → request stored
    on the server with configuration, image, contact and the same price as shown.
  - Configurator: dimension labels on/off, out-of-range input corrected with an explanation, impossible combination
    blocks the request and flags the step, arrow-key tabs, camera buttons, text alternative of the 3D view, **shared
    link restores the exact configuration and price in a new tab**, room mode with wall color and person, compare
    with difference table, phone layout (3D view and step tabs stay pinned, price bar always visible, touch stepper,
    room settings), WebGL disabled → clear fallback, still usable.
  - Downloads: snapshot PNG, **PDF quote** (title, demo label, total matches the configurator to the cent, cut list,
    embedded image; checked with `pdfplumber`), **GLB** (glTF 2.0 header, meshes and textures, no room geometry).
  - Site: cookie notice (appears, persists, reopens), skip link and focus ring, phone menu with Escape, contact form
    errors and success, no-JavaScript fallback message, tampered reference ignored, structured data (`Product` with
    `AggregateOffer`, `BreadcrumbList`, `FAQPage`), unique title and description on every page, all 34 internal
    links return 200, every image loads and has an alt attribute.
  - Server: gzip and brotli, CSP meta tag with hashes plus security headers, immutable caching of hashed assets,
    custom 404 with status 404, path traversal blocked, trailing-slash redirect, 405 for GET on the API, robots.txt,

is light; **it is not a phone benchmark** (see limitations).

## What's not perfect / limitations

- **Frame rate was not measured on a real phone.** The techniques for it are in place (render on demand, capped and
  adaptive pixel ratio, smaller textures and shadow maps on phones, shared materials, worker-generated textures).
  The only numbers available here come from headless Chromium rendering WebGL in software (SwiftShader, see
  “Tests”), which is far slower than any phone GPU and says nothing about 60 fps on a mid-range phone.
- **The 3D code is big.** three.js alone is ~240 KB gzipped. It only loads on the configurator page (content pages
  ship ~2 KB of JavaScript), but on a slow mobile connection the first 3D view takes a few seconds; until then the
  page shows a loading message and the options and price already work. Textures are generated on the device
  (≈0.2–0.8 s per wood in a Web Worker), not downloaded.
- **Generated wood is convincing at furniture scale, not photo-real up close.** All parts of one piece are cut from
  the same virtual 3.2 m panel (with different offsets), and pine knots can look like spots when you zoom in close.
- **The structural checks are engineering estimates**: simply supported beams, literature averages for stiffness,
  no composite action between top and apron, no creep calculation, joints and legs not checked. They are deliberately
  conservative (a 2.40 m table with a 30 mm top on an apron gets a warning), and a real workshop would still check
  the drawing.
- **No email is sent.** Requests are stored as JSON + JPEG in `data/`. For production, connect SMTP or a CRM at the
  marked spot in `src/server/api/inquiry.ts`. Rate limiting is in memory (one server process).
- **AR is not included** (see the configurator table). The GLB export is the basis for it.
- **The room is simple**: two walls, three floors, five wall colors, no windows or doors; the scale figure is a
  neutral mannequin.
- React Three Fiber 9 logs a console *warning* (not an error) that `THREE.Clock` is deprecated in three.js r18x;
  it comes from the library and disappears with a future R3F release.
- Legal notice and privacy policy are placeholders with the right structure, not legal texts.
- No Lighthouse score (Lighthouse isn't installed here); page weight, request count and load times were measured
  directly in the browser instead.
